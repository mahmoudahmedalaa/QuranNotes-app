QuranNotes Noor RAG — Executive Technical Design & Operator Guide

Purpose: understand the architecture at an executive-technical level, know where the important controls live, and be able to inspect the real Firebase/Vertex configuration without drowning in implementation detail.

Core design: Noor retrieves approved Quran/tafsir evidence before generation. The model is allowed to synthesize naturally, but it is not supposed to make unsupported religious claims. Specific failures become eval cases; general failure classes become reusable runtime capabilities.

1. System architecture

User question + validated conversation state ↓ Auth / App Check / entitlement / quota / idempotency ↓ Query understanding + contextual rewrite ↓ Hybrid retrieval (Vertex semantic embeddings + lexical search) ↓ Ranking / deduplication / source balancing ↓ Answerability — can the evidence really answer? ↓ Selected evidence blocks (S1, S2, ...) ↓ Grounded generation with Gemini ↓ Structural + citation + generic answer-quality validation ↓ ANSWER / INSUFFICIENT_EVIDENCE / POLICY_REFUSAL / TEMPORARY_FAILURE

3. Knowledge-base pipeline

Noor's reviewed corpus currently comes from two tafsir datasets: Ibn Kathir (abridged English) and Al-Sa'di Arabic. Corpus construction is deterministic until production exact-token promotion.

Reviewed tafsir files ↓ Normalize ↓ Canonical units ↓ Chunking ↓ Lookups + verse/source metadata ↓ Vertex exact-token validation / promotion ↓ Embeddings (768 dimensions) ↓ Firestore production corpus

Important identity distinction: the local deterministic corpus has 9,057 chunks with hash f6efa40d...adbca5. Production exact-token promotion creates 9,248 chunks with hash 5fadc4e1...f1ab528. The sources are the same; Vertex token counting creates additional splits for chunks exceeding the 1,400-token ceiling.

5. Verification harness

One of the main lessons from building Noor is that local unit tests are not enough to certify a RAG system. Noor deliberately separates three levels of proof.

LayerCommandWhat it proves
Structural / deterministicnpm run noor:verifyCorpus integrity, tests, build/contracts and deterministic exact cases.
Real semantic retrievalnpm run noor:verify:retrievalReal Vertex embeddings against the promoted Firestore corpus without generation.
Authenticated livenpm run noor:verify:liveAuth + App Check + retrieval + generation + citations + conversation-state behavior.
stable-v1 → candidate → deterministic verify → semantic preflight → targeted deployment → authenticated live verify → stable-v2 OR rollback

6. The failure classes we care about

Regression exampleWhat it actually tests
Noah vs NuhSemantic equivalence/transliteration rather than literal word matching.
Al-Baqarah “its significance”Anaphoric follow-up resolution and contextual retrieval.
Football scoreAnswerability and clean abstention when semantically noisy Quran chunks appear.
Riba follow-upSequential generation, citation validation, persisted conversation state and contextual follow-up.
Wudu ambiguityGeneric grounded-answer quality and preservation of material qualifications — not a Wudu-specific production branch.
Architecture rule:
Specific failure → eval case.
General failure class → reusable runtime capability.

This prevents Noor from becoming a pile of hardcoded topic patches.

7. High-value tuning levers

  1. Corpus quality: what sources Noor is allowed to draw from.
  2. Chunking: whether retrieved units contain enough context without becoming noisy.
  3. Retrieval/ranking: top-K, thresholds, lexical terms, fusion and answerability.
  4. Generation contract: how freely Gemini synthesizes evidence.
  5. Generic quality/grounding: whether the answer actually responds, remains supported and preserves material qualifications.
  6. Evals: regression cases that prove changes generalize rather than simply fix one prompt.
  7. Observability: request IDs, query rewrites, evidence IDs, status, latency and failure categories.
